08

Directrices para seguir ejecutando

1

Un incremento por vez

No pedir “construir toda la app”. Pedir una historia pequena: modelo, endpoint, pantalla, verificacion.

2

TDD en backend

Cada endpoint nuevo debe empezar con una prueba que falle, luego implementacion minima y despues refactor.

3

MVVM en mobile

La vista no debe cargar logica de API. La pantalla consume un hook/view-model y el hook llama servicios.

4

Accesibilidad primero

Texto grande, botones claros, pocas acciones por pantalla, labels accesibles y alto contraste.

5

Validacion triple

Backend tests, lint/verificacion mobile y evidencia visual en web, telefono o emulador.

6

ClickUp actualizado

Cada sprint debe reflejar alcance, fuera de alcance, checklists y evidencia de cierre.

Prompt recomendado para el siguiente agente

CONTEXTO: MediVoz esta en Fase 4. Monorepo con backend FastAPI y mobile Expo JavaScript. Ya existe GET /health y pantalla HealthScreen.

OBJETIVO: Implementar Sprint 1 - recordatorio basico.

ALCANCE: Crear modelo SQLite para Medication, Reminder y DoseLog; endpoints POST/GET de medicamentos, POST de recordatorios, GET /reminders/today y POST /reminders/{id}/taken; pantalla accesible para registrar medicamento y ver proxima toma.

NO HACER: No autenticacion, no voz, no inventario, no reportes, no catalogo CUM completo, no alarmas en segundo plano.

CRITERIOS DE ACEPTACION: Pruebas backend pasan; mobile pasa check:js-only y lint; app muestra proxima toma; se puede marcar tomada; evidencia visual registrada.

VERIFICACION: pytest -v en backend, npm run check:js-only y npm run lint en mobile, validacion visual en Expo Web o Android.
